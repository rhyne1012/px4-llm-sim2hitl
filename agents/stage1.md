# 第 1 段「需求與規格」：AI 怎麼和人談

> 用途：第 1 段怎麼談，包括 1.1 飛機模型與配平、1.2 算法、部署與驗收（PX4 接法、一頁規格）、最小打通，以及本地化、ULog 兩個建議。
> 什麼時候讀（必讀）：談需求、寫一頁規格、換飛機、新算法，或開始自己的專案、fork 時。
> 可以跳過：只跑既有的流程、只看結果或只改文件時。
> 從 [AGENTS](../AGENTS.md) 搬來，原文不改，只改了連結。每一項要求由哪一邊回答、怎麼判讀，在 AGENTS 的 C5。

### 第 1 段「需求與規格」：最重要，先和人把整個工作流程談完

AI 先查好現況、提出建議，只跟人確認**目標、選擇與成功條件**：

1. **先聽**：想做什麼、要飛什麼情境、怎樣算成功。
2. **1.1 飛機模型與配平**：是哪一架飛機、和 SkySurfer 差在哪裡（外型、重量、重心、慣量、氣動、舵面配置）。舵面配置不同時（例如飛翼、V 尾），現在固定的五路輸入（左副翼、右副翼、升降舵、方向舵、油門）要跟著改。改完：重新產碼、四道檢查、配平與放手測試（`sitl/trim.py`）。刻意改了模型後，「對錄製參考資料的比對」本來就會不同（它只報告、不擋）；確認同次 Simulink 對照通過後，再重錄參考資料。也要提醒使用者，有兩樣是照 SkySurfer 定的，可能要跟著改：模型的簡易地面（重心一個接觸點、摩擦 0.2、地面不產生力矩，見 [plant README](../plant/README.md)「地面」），以及 HITL 自動起飛的數字（`hitl/aircraft/<飛機>/profile.json` 的 `automation`，見 [autotakeoff README](../hitl/autotakeoff/README.md)）。SITL 不跑起飛，新飛機第一次起飛在 HITL 試。重心、氣動表的力矩參考點、中性點與 MAC 見 [plant README](../plant/README.md)「重心與氣動作用點」：使用者說「重心往機頭／機尾多少」或「在 MAC 幾 %」時，照那裡換算成 `CG_m`，並告訴他新的靜穩定度。
3. **1.2 算法、部署與驗收**：
   - **先讀鎖定版本的 PX4 原始碼，再和使用者討論接法**：依使用者要開發的東西，整理 PX4 現在的控制鏈（固定翼大致是：導引／模式管理 → 高度與速度 → 姿態 → 角速度 → 控制分配）、模式與相關模組，找出這次可行的方案；每個方案用白話說明要不要改 PX4 原始碼、能不能切回原生、失效保護誰負責、Flash 空間、SITL 要模擬哪些部分。可能的例子：OFFBOARD（交出去幾層由旗標決定，模組也能在韌體內自己發 OFFBOARD 訊號，不一定要外接任務電腦）、用專案的 patch 機制修改或拿掉原生模組、PX4 的外部模式。**這些只是例子，不是只有這幾種**；方案由使用者選，AI 依原始碼查證可行後才開始。`modules/src/guidance_template` 是其中一種接法的範例，只用來讓人有概念；
   - 預想 SITL 與 HITL 會碰到的問題：SITL 用真值、不經 EKF；HITL 編進客製韌體、用 FC 上 EKF 的估測；和現有飛行模式怎麼共存；Flash 空間（原生韌體已用約 98 %）；HITL 沒有實體遙控器，PX4 的「遙控」是自動飛手送的搖桿，一停就觸發遙控斷訊保護（SITL 沒有 Commander，驗不到），所以新算法從哪個模式進、結束在哪個模式，要和飛手的規則對得上（[autotakeoff README](../hitl/autotakeoff/README.md)）；
   - 談好：用哪塊飛控、HITL 是否已設好；新算法何時接手、怎麼退出、失效時怎麼回到原生；用什麼動作證明它真的有作用。**不是已有配方的飛控**（目前有 Pixhawk 6C 與 Cube Orange+）時，先照 [fc README](../fc/README.md) 的清單查：預設韌體有沒有 HITL 要的 `pwm_out_sim`（Cube Orange+ 就沒有）、FC 回報的板子身分、bootloader 的 USB 名稱、開機腳本設的參數、flash 餘裕；查完再建這塊飛控的配方；
   - **「怎麼部署」是第 3 段一條龍的前提**；
   - 寫成模組 README 的一頁規格：這次要證明什麼（見 [AGENTS](../AGENTS.md)「下結論之前」）、目標、接法、SITL 與 HITL 各自的驗收指標。兩邊估測來源不同，比的是表現與差距，不要求逐點相同。最小打通只要證明接法通、模組真的有作用，不需要和原生比較或做統計。
   - **每一項要求都寫明由哪一邊回答**：搬到 [AGENTS](../AGENTS.md) 的 C5（每次判讀與寫報告都要，留在入口）。

不替使用者預先決定客製方式；把要想的問題提出來，依 PX4 原始碼給建議。

**建議先做「最小打通」**：開發位置確定後（例如只做導引），先不寫正式算法，而是架好開發框架，用一個極簡的版本（例如把 PX4 原本的導引換成一個很簡單的測試）走完 SITL → 編韌體 → 燒錄 → HITL 一次，並記錄下來。之後每次修改都交給自動化（第 2 段的指令與第 3 段的 `deploy-test`），不必每次重新摸索接法，可以省下很多 token。把這個建議告訴使用者，由使用者決定要不要做。

**建議人把這包本地化**：這包是給大家用的通用套件。拿它開始自己的專案時（例如 fork 一份），建議人把它改成自己的：自己的飛機（模型、`hitl/aircraft/<飛機>/`、名稱）、自己機器的路徑與設定（環境變數 `SIM2HITL_*` 或設定檔）、自己的飛控與配方、自己的驗收標準與自動化腳本，並寫進專案文件。之後的 AI 讀文件就知道，不必每次重新查，省 token。由人決定要不要做、做到哪裡。

**建議使用者用 ULog 看結果**：SITL、HITL、實機都產生 ULog，AI 用 Python 自動判定，人用 MATLAB 畫圖檢查；好處與工具見 [analysis README](../analysis/README.md) 的「ULog 工具包」，向使用者說明後由他決定。
