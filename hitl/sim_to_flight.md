# 從模擬到實飛：一個衍生專案走完整圈之後，對框架的想法

更新：2026-10-26。來源是衍生專案 SkySurfer（attitude doublet 跑道任務，Cube Orange+，PX4 v1.17.0）。它在 2026-10-24～26 走完一整圈：

- SITL；
- Cube HITL，再加上讓實體舵面跟著動；
- 切到實飛，第一次實飛；
- 用飛行資料把轉動慣量和重心改回模型。

框架的流程目前寫到 3.2 出場檢查（還沒完成）為止。這份是走完一圈之後的想法：框架怎麼延伸到實飛，實飛的資料又怎麼接回模型。

- 除了標「框架現在有」的地方，下面都是建議，不是現有功能。
- 數字只代表那架飛機、那個配方、那幾天。
- 和 [workflow_lessons.md](workflow_lessons.md) 的關係：那裡第 6 點的切換做法（另外燒實飛韌體），被這裡第 1 點取代。

## 0. 整圈，以及三個想法

```
① 飛機模型（Simulink）── 產碼、四道檢查 ──▶ 模型 release
② SITL（電腦版 PX4，lockstep）
③ HITL（實體 FC）──▶ 3.2 出場檢查：HITL 時讓實體舵面跟著動（拆槳）
④ 只改參數切到實飛（人在視窗按 y）──▶ ⑤ 實飛（任務紀錄＋飛控紀錄）
⑥ 用飛行資料分析配平、不對稱、轉動慣量（以 HITL 為尺）
⑦ 改模型、記下來源 ──▶ 回到 ①：配平、SITL、HITL 再驗一次
```

- **閉環**：框架現在是一條直線（模型 → SITL → HITL），終點停在 HITL。實飛應該是流程的一段，而且實飛的資料要流回模型。
- **每個產物都指得出依據**：
  - 模型 release 指向改它的那趟飛試；
  - 配方的每個值指向它的來源（模型配平、使用者、實飛資料）；
  - 任務紀錄指向它的飛控紀錄。
- **同一把尺延伸到分析**：README 說 SITL 和 HITL 用同一把尺。實飛也一樣：同一支分析程式同時跑實飛和 HITL 的記錄，兩者的差就是模型和真機的差（第 6 點）。

## 1. 一份韌體、兩組參數：HITL 和實飛只差參數

- **做法**：
  - Cube 的 `hil` 板子變體就是 `default` 加上 `pwm_out_sim`。rcS 只有在 `SYS_HITL` > 0 時才啟動 `pwm_out_sim`；`SYS_HITL=0` 時照 `default` 啟動 `pwm_out` 和真的感測器。
  - 參數表是 `default` 的 1,962 個再加 17 個 `HIL_ACT_*`，其他預設值完全相同。
  - 所以實飛配方和 HITL 配方用同一份韌體、同一個開機檔，切換只寫參數。步驟：
    1. 讀回參數；
    2. 核對韌體身分和記憶卡上的開機檔；
    3. 逐項列出計畫；
    4. 人在視窗輸入 y；
    5. 寫入，每個值都要讀到回音，`GPS_1_CONFIG`、`SYS_HITL` 最後寫；
    6. 重開，再讀回一次，`check_params` 要 PASS。
  - 實測（2026-10-26）：HITL → 實飛寫 12 個值，花 20 s；實飛 → HITL 寫 11 個值，花 27 s（`GPS_1_CONFIG` 由 HITL 開機自己寫回 0）。
- **為什麼**：
  - 在場地不用重新燒錄。
  - HITL 測過的就是會飛的那份二進位：同一個模組、同一份 patch。
  - 來回切幾次都可以。
- **要注意**：
  - flash 多用 0.35 %（98.55 → 98.9 %）。
  - 開機檔兩邊要相同，否則只切參數不夠。工具要檢查，不同就停下。
- **給框架的建議**：
  - 把 `hil` 變體當成「HITL＋實飛」共用的標準韌體，配方成對（HITL 和實飛用同一份 `firmware.json`）。
  - 加一個通用的只改參數切換工具，給人用的桌面捷徑也一起做。
- **框架現在有**：`deploy/check_params.py`、Cube 的 `hil` 變體 patch。沒有切換工具，workflow_lessons 第 6 點只寫了做法。

## 2. 3.2 出場檢查：HITL 時讓實體舵面和馬達跟著動

- **做法**：
  - PX4 v1.17 在 HITL 時不會鎖住實體輸出：lockdown 只給多旋翼拋飛用，HIL 輸出模組本來就忽略它。
  - 所以 HITL 配方加上實飛的輸出設定（`PWM_MAIN_FUNC*`、反向、中立、電調範圍、更新率），就能邊飛 HITL 邊看真的舵面和馬達。
- **為什麼**：方向、反向、中立、配平量都用眼睛看得到。這次就是看著實體舵面，才發現 HITL 時升降舵一直上偏約 10°，也就是重心 50 mm 的模型很頭重。使用者之後把實機重心移到 65 mm（說明書建議約 71 mm），飛試的配平量和改成同樣重心的模型相符（第 6 點）。
- **要注意**：
  - 一定要拆槳；電調有電時，馬達會照油門轉。
  - 伺服軌要有電，舵機才會動。
  - 沒人看著的自動 HITL 不用這個配方。
- **給框架的建議**：
  - 當成 3.2 的正式做法，配一份清單：每個模式下各軸打一次，確認方向。
  - **量出每個舵面在 ±1 時的實際角度**。模型用的是假設值（例如升降舵 27°），第 6 點的分析要靠這個數字。

## 3. 實飛前：工具保證的值，和只能人看的值

切換工具 PASS 只保證兩件事：配方寫的值都對，其他參數都是韌體預設。下面這些工具看不到，要人看：

- **FC 自己的校正（`fc_owned`）**：
  - 遙控器校正（這台的 ch6、ch7 還是預設的 1000／2000）；
  - 感測器方向（`SENS_BOARD_ROT`、外接羅盤）；
  - 電池分壓；
  - 空速零點和皮托管模型。
- **外部裝置的參數**：例如 DroneCAN 空速節點上的 `ARSPD_TYPE`。
- **接收機自己的失效保護**：斷訊時要送 failsafe 旗標，不能保持最後的值，否則 PX4 不知道斷訊。
- **失效保護的選擇**：
  - 遙控器斷訊時，Mission 中也會 RTL（`COM_RCL_EXCEPT` 0）；
  - 低電量只警告，不會回家（`COM_LOW_BAT_ACT` 0）；
  - 安全開關停用（`CBRK_IO_SAFETY`）；
  - 沒有 GPS 也能解鎖。

踩過的坑：

- **`COM_RC_IN_MODE` 預設 3**：開機後先有效的那個來源會鎖到重開為止，另一個完全不理。實測：QGC 虛擬搖桿先連上，遙控器整趟沒作用；之後 QGC 搖桿斷了 0.5 s，觸發「手動控制遺失」（先 Hold 再 RTL），而且不會改用遙控器。有實體遙控器的配方要改成 5（遙控器優先）。
- **QGC 的 USB 自動連線**：打開時會佔住序列埠，owner 就連不上 FC。實飛現場常常會打開它，回到 HITL 前要關掉。
- **配平會隨空速放大**：`TRIM_ROLL/PITCH/YAW` 和速率控制器的輸出（包含積分器）都會乘上 (V_trim / max(V, V_stall))²。所以在地上和手擲時會被放大好幾倍：`TRIM_PITCH` 0.4 在地上變成 1.84，舵直接打滿。
  - 重心造成的力矩用 `TRIM_*` 補是合理的。
  - 氣動上的歪（機翼扭轉、副翼中立不一致）用固定偏移 `CA_SV_CS*_TRIM` 補比較對。

- **給框架的建議**：從配方和 `fc_owned` 產生一份「實飛前人工檢查表」，附上讀回的現值，存進那一趟的紀錄。

## 4. 實飛的紀錄，以及大檔放哪裡

- **做法**：
  - 實飛也建任務紀錄（`record --ulog`），和 HITL 同一種格式，在同一份總表裡。
  - 飛控紀錄放 GitHub Release，每趟一個：
    - tag 是 `flight-test-<時間>`，標題是「飛試 …」，說明寫明是實機飛試；
    - 附紀錄連結，以及壓縮前、後兩個 SHA-256；
    - 不設成 repo 的最新版本；
    - 上傳後要下載回來核對過，才寫進紀錄。
  - `record --fetch-logs` 讓別台機器把缺的飛控紀錄補回本機。
- **為什麼**：
  - 15 分鐘的實飛，飛控紀錄就有 116 MB，超過 GitHub 單檔 100 MiB 的上限。Release 不佔 repo 大小，總量和下載量也不限。
  - git clone 和 mirror 都不會帶 Release 裡的檔案，所以一定要有下載工具。
- **要注意**：
  - `SDLOG_PROFILE` 的高頻位元，是第 6 點分析做得出來的原因：角速度和舵面命令有 271 Hz，預設只有 10–50 Hz。它也是檔案大的原因，約 8 MB／分鐘。試飛時保留，例行飛行可以關掉。
  - 飛控紀錄裡有飛行場地的 GPS 軌跡。repo 公開時，Release 也會跟著公開。
- **給框架的建議**：
  - 紀錄系統（workflow_lessons 第 1 點）加上「實飛」，以及「大檔放 Release、能取回」。
  - 實飛紀錄加固定欄位：重心、重量、電池、風、飛手筆記、有沒有拆槳。

## 5. 實飛時的意外，要先想好怎麼處理

- **硬體錯誤當機**：
  - hard fault 會在記憶卡留下 `fault_*.log`，PX4 開機檢查到就不准解鎖（`COM_ARM_HFLT_CHK`）；刪掉以後要重開才會解除。
  - 這次是 USB 那條 MAVLink（`mavlink_if2`）在 QGC 直接連 USB 時當掉，類型是 bus fault。
  - 框架 owner 的記憶卡寫入只准在 `SYS_HITL=1`，所以實飛設定下改用 MAVLink FTP，經 owner 的 agent 埠刪除；刪之前先存一份。
  - 要分析當機，需要那一版韌體含除錯符號的 ELF。**清理建置資料夾時要保留**，這次就是因為刪掉了而查不出原因。
- **EKF 切換**：手擲那幾秒，EKF 的實例 0 和 2 出現速度融合的數值錯誤，自動換到沒出錯的實例 1。這類事件要列在紀錄裡。
- **其他會觸發的保護**：地理圍欄、低電量、姿態超限（`FD_FAIL_*`）在實飛都可能觸發，紀錄要自動列出來。
- **給框架的建議**：
  - 做一個「實飛設定下的維護」小工具：列出記憶卡、保存後刪除當機紀錄、重開。
  - 規則寫清楚自動化在 `SYS_HITL=0` 時能做什麼：讀取可以；寫入只限人確認過的少數動作。

## 6. 從飛行資料回到模型：以 HITL 為尺

- **問題**：
  - 用整趟資料做方程誤差迴歸估轉動慣量，結果會偏：閉迴路加亂流，控制器對陣風的反應和舵面量是相關的。
  - 同一支程式套在**已知慣量**的 HITL 記錄上，也把 Iyy 估成 0.12–0.14，真值是 0.087。
  - 實機的 Ixx 甚至估出 0.8，物理上不可能。
- **可用的做法**：
  - 只看 doublet 段，用 output-error 擬合簡單的模型：滾轉用一階，俯仰用短週期。
  - 同一支程式同時跑實機和 HITL 的記錄（同一個控制器、同樣的 doublet），比兩者的比值。
  - 挑和慣量無關的量：
    - 穩態滾轉角速度／單位副翼，實機 262–285 °/s，模型 250–255 °/s。這表示模型的「副翼效率對滾轉阻尼」的比例是對的。
    - 舵機延遲和滾轉模態分不開，只能估兩者的總和：實機 30–35 ms，模型 95–100 ms。
- **SkySurfer 的結果**：
  - 轉動慣量：Ixx ≈ 0.023、Iyy ≈ 0.05，約是原模型的一半。Izz 沒有方向舵的激勵，估不出來，改用 Ixx＋Iyy。
  - 機身不對稱：直飛要一直補 1/4 行程的右副翼。
  - 重心從 50 mm 改成 65 mm 後，模型在 16 m/s 的配平升降舵是 0.221，和實機直飛時的 +0.236 相符（原本是 0.314）。
- **要注意**：
  - 慣量的推論，依賴 AVL 的阻尼和舵面導數，以及假設的舵面行程。
  - 樣本少：只有 3 次 roll、2 次 pitch doublet，而且有亂流。
  - 最準的作法是用雙線擺（bifilar pendulum）直接量。
- **給框架的建議**：
  - 做一支「實飛 vs 模型」分析工具：自動找同一個配方的 HITL（或 SITL）記錄當對照，輸出比值和範圍，不要只給一個數字。
  - doublet 模組加上偏航軸，才能量 Izz 和方向舵效率。
  - 3.2 量出來的舵面行程（第 2 點）存進飛機的設定，讓分析直接讀。

## 7. 改模型要記下來源，被模型牽動的東西要一起查

- **做法**：把慣量和重心改回模型時，三個地方都要寫清楚：
  - 寫在：模型初始化檔的註解、plant README、那一趟飛試紀錄的結論；
  - 內容：依據哪一趟（紀錄名稱、Release tag）、估計範圍、假設、舊值，以及新的模型 release 編號。
- **被模型牽動的東西**：
  - **配方裡從模型配平算出來的值**（`TRIM_PITCH`、`FW_DTRIM_P_VMAX`、`FW_PSP_OFF`、`FW_THR_TRIM`）：重心一改就全部不對。例如 15 m/s 的配平升降舵從 0.404 變成 0.274。
  - **在舊模型上調的參數**（例如姿態的時間常數）：新模型的反應比較快，HITL 的 doublet 結果會和以前不一樣。
  - **驗證程式裡寫死的模型常數**：`validate_library.py` 的發散保護測試要求「7.068 s 以前觸發」，那是原始模型撞地的時間。重心改了以後，撞地延到 7.44 s，觸發原因一樣（撞地時加速度超出範圍），整個發布卻被擋下。衍生專案改成「30 s 內以 code 3 觸發，並記下時間與原因」。
- **給框架的建議**：
  - 模型 release 的 manifest 加一個「來源」欄位（例如 `flight-test-…`）；任務紀錄的「和上一趟的差別」要列出模型 release 換了。
  - 配方裡從模型推出來的值，標明「模型配平，重心 …」；模型一改就提醒重算。
  - 檢查程式裡和特定模型綁死的數字，改成和模型無關的條件，或放進飛機的設定（`hitl/aircraft/<飛機>/`）。

## 8. 建議的順序

1. 一份韌體的 HITL／實飛配方對，加上只改參數的切換工具（第 1 點），第 5 點的維護工具一起做。
2. 3.2 出場檢查：HITL 時讓實體舵面跟著動，並量出舵面行程（第 2 點）。
3. 實飛的任務紀錄，飛控紀錄放 Release、能取回（第 4 點）。
4. 實飛前的人工檢查表（第 3 點）。
5. 以 HITL 為尺的「實飛 vs 模型」分析，doublet 加偏航（第 6 點）。
6. 模型修改的來源，以及被它牽動的東西的檢查（第 7 點）。

衍生專案裡可以參考或移植的實作：

- `hitl/switch_session.py`（一鍵切換）、`deploy/flight_switch.py`；
- `hitl/host/records.py` 的 `publish_log`、`fetch_logs`；
- 配方 `04_doublet_cubeorangeplus_flight`（實飛）、`05_doublet_cubeorangeplus_hitl_surfaces`（HITL 帶實體舵面）；
- `hitl/tests/validate_library.py` 改過的發散保護測試。
